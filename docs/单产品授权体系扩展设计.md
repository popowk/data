# PhoneHub 单产品授权体系：代理商隔离、权限与密钥轮换设计

> 日期：2026-11-17  
> 状态：设计基线，**不是已上线功能**。开发版本当前为 v0.5.7。  
> 原则：仅管理 PhoneHub 这一套授权；明确**不开发多软件产品授权、产品目录、跨产品配额或跨产品订单**。

## 1. 实施边界

既有客户账号、设备绑定、授权截止、平台权限、AI/MCP/Skill 配置及现有签名机制继续保留。套餐只管理开户电脑与手机额度，不涉及价格、支付、购买订单、自动续费。系统内新增逻辑必须遵循默认拒绝、服务端校验、最小授权和迁移可回滚原则。

不能把“分组”直接当作“代理商”：分组当前是客户分类且可批量授权，缺少租户身份和数据访问边界。即使某个页面隐藏了其他客户数据，也**不等于** API、日志、设备、文件下载已实现租户隔离。

## 2. 代理商数据隔离：分阶段实施

### 阶段 A：只读覆盖面盘点（先做）

- 编制所有管理端页面、POST 操作、客户端 API 和数据表的访问矩阵。特别覆盖：客户账号、分组、会话、安卓设备指纹与黑名单、敏感信息查看、客户端日志、操作包、发布版本、AI/MCP/Skill 全局开关、更新和签名、备份密钥、审计。
- 列出每种操作的对象归属及查询方式：按客户 ID、设备 ID、日志 ID、会话 ID、授权码、分组 ID 访问时，服务端必须验证对象属于当前授权租户。
- 现阶段继续只有平台主管理员和现有普通管理员，不向任何代理商开放后台入口。

### 阶段 B：新增租户模型，**默认不启用代理商登录**

建议数据结构：

| 新结构 | 目的与约束 |
|---|---|
| `phonehub_tenants` | 代理商 ID、名称、状态、创建时间；禁止删除仍有客户的租户 |
| `phonehub_users.tenant_id` | 客户归属；旧客户默认归属平台保留租户，不自动分配给代理商 |
| `phonehub_admins.tenant_id` | 管理员归属；平台 owner 不受租户范围收缩 |
| `phonehub_groups.tenant_id` | 分组必须与客户处于同一租户；禁止跨租户批量修改 |
| 审计表的租户上下文 | 明确记录动作发起者、对象租户及操作类型，不记录密钥明文或敏感设备信息 |

数据库变更遵循 MySQL 5.7 的幂等迁移，避免生产升级直接对大量数据做阻塞重写；先补字段、填充旧数据、核对数量，再加约束和索引。所有原有客户保留原账号、密码、会话和套餐标签。

### 阶段 C：服务端权限强制执行

- 首先定义角色矩阵：`owner`（平台主管理员）、`admin`（平台运营管理员）、`agent_admin`（代理商管理员）、`agent_operator`（代理商只读/受限操作员）。首批代理商默认不允许访问系统更新、签名、备份密钥、全局 AI/MCP/Skill 开关及全局设备黑名单。
- 强制每个有业务数据的查询和写入绑定租户条件；服务端验证，不依赖 URL、表单的隐藏 `tenant_id`、前端菜单或代理服务器的路径。
- 客户名和设备/日志等全局唯一标识的冲突规则单独定义；避免仅凭“对象不存在”错误泄露其他租户的数据。
- 设备移交客户、跨代理商转移、代理商停用/恢复必须有平台 owner 专用流程、审计和会话撤销策略。
- 代理商权限默认最小化，不默认继承平台管理权限；不允许代理商给客户授予超出平台代理权限的能力。

### 阶段 D：安全验收和灰度

必须覆盖跨租户 IDOR、分页统计侧漏、直接 POST/API 越权、并发更换客户归属、设备日志查询和批量修改误操作。先在隔离库用样本租户执行自动化测试，并核对旧客户数据条数与授权。上线时先只允许测试代理商登录，失败时可关闭新角色入口，不能通过清空租户字段来“回滚”。

## 3. 后台权限矩阵

| 操作 | 平台 owner | 平台 admin | 未来代理商 |
|---|---|---|---|
| 全局系统更新、Ed25519 签名、备份密钥 | 允许 | 禁止 | 禁止 |
| 全局 AI/MCP/Skill 开关与签名发布 | 允许 | 禁止或按现有逻辑收敛 | 禁止 |
| 套餐模板新增、修改与启停 | 允许 | 禁止 | 禁止 |
| 平台全部客户与分组 | 允许 | 现有授权范围 | 禁止 |
| 自有租户客户查询及授权管理 | 允许 | 按运营角色范围 | 待权限矩阵确认后开放 |
| 敏感设备信息查看与全局拉黑 | 允许并审计 | 最小授权 | 默认禁止 |
| 审计检索及导出 | 允许 | 仅授权范围 | 仅自身租户非敏感记录 |

**安全前置条件：** 先完成上述完整的服务端操作覆盖检查和越权自动化测试，才能在实际界面加入“代理商登录”。不要先制作代理商前端，再补数据库鉴权。

## 4. 套餐管理的后续深化

- 现有套餐模板及“开户时套餐”的标签继续保留；模板调整只影响以后新开户，不能批量回写老客户。
- 增加单一客户的“开户模板额度 / 当前实际额度 / 最近调整时间”三者区分；后续可在审计中记录调额原因，但不得写入敏感明文。
- 分组批量修改已在 v0.5.7 增加服务端预览与成员快照校验；下一步增加逐字段差异数量统计和影响范围分页。
- 只扩展 PhoneHub 的电脑名额、手机名额及已有授权字段；**不增加多产品 SKU、跨产品权限或订单付款**。

## 5. Ed25519 固定公钥轮换与备份接收密钥

### 服务端自更新签名

**不得直接覆盖正在使用的固定信任公钥。** 现有更新程序可能只认识旧公钥。轮换设计应先支持可信的过渡发布，再用旧密钥签名的受信软件更新引入新信任规则；验证新密钥及过渡期的旧签名兼容性，完成灰度后才正式废止旧信任。要覆盖伪造、篡改、版本回退、更新中断与旧客户端升级路径。严禁把私钥放进 Web 可访问目录或 Git 历史。

### Curve25519 备份接收密钥

现有 `storage/backup-recipient.pub` 只持久化公钥，私钥已在第一次初始化时离线交付，不允许通过后台重新下载或自动重建。若以后必须轮换，应采用可识别旧备份版本/接收公钥指纹的机制，旧备份保留对应旧离线私钥；新备份切换到新公钥前要验证加密/解密往返。**不能**把替换公钥等同于迁移历史加密备份。

## 6. P1 运维体验与 P3 性能

- v0.5.6 已将客户列表改为服务端 30 条分页，运营概览改为聚合统计；继续以真实数据规模记录 P95 响应、慢查询和索引效果，不先虚报性能收益。
- 审计和客户端日志采用带租户边界的分页查询、保留期限及脱敏导出；历史数据清理需要管理端明确确认，不做未经授权的自动删除。
- 真正的原子升级需要单独评估部署目录、软链接和 PHP-FPM/OPcache 缓存，不宣称现有逐文件替换天然零中断。
- 备份自动调度监控和异地备份状态不在当前交付范围；只继续维护既有 CLI 加密备份及隔离恢复流程。

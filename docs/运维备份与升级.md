# PhoneHub 运维、升级与恢复指南

> 此文档供授权管理后台运维使用，不是 Windows 客户端接入说明。网站根目录的用户自定义 README.md 不会被升级器覆盖。

## 1. 当前升级器的保护边界

升级器仅从固定 HTTPS 镜像 `https://git.wksite.cn/popowk/data` 下载程序源码 ZIP，并使用固定白名单处理文件：

- **升级前**：检查 ZIP 清单是否齐全、每个 PHP 文件可解析、文件大小、目录是否允许写入，并将全部更新文件暂存到 `storage`。
- **备份**：先复制现有程序文件到 `storage/backups/<时间>-<随机串>`，再逐个替换，最后写入 `version.json`。
- **验证与恢复**：校验替换后的 SHA-256；若安装阶段失败，尝试从备份恢复已修改的文件。
- **数据保护**：升级器不会替换 `README.md`、`storage/config.php`、任何其他 `storage` 内容或用户数据库。

限制：每个目标文件的 rename 是单文件原子操作，并非整个网站的原子切换。运行中的请求仍可能短暂读到不同版本的文件。若 PHP 进程被强制结束、机器断电或存储损坏，进程内自动回滚可能无法执行。要实现完整的不中断发布，需要在服务器部署层增加版本目录和原子软链接切换，不能直接假定宝塔现有目录支持。

更新源仍是 main 分支 ZIP。**现已支持固定公钥 Ed25519 独立签名验证，但出于升级兼容性，未配置公钥的旧站点仍为 HTTPS 镜像兼容模式。** 只有由运维明确安装了 `storage/self-update-trust.pub`（32 字节原始 Ed25519 公钥）后，才会强制校验 ZIP 内的 `deploy/self-update-manifest.json` 和 `deploy/self-update-manifest.sig`；缺签名、签名不可信、版本不一致或文件摘要不一致一律拒绝更新。后台会显示当前是否已完成独立验签。不要把“有这个功能”误认为生产环境已经启用签名更新。

### 后台一键初始化签名（v0.5.2，推荐）

主管理员直接打开「系统更新 → Ed25519 签名密钥管理」，输入一次性 GitHub Token（需要 \`popowk/data\` Actions Secrets 写权限与工作流触发权限），点击「生成密钥并自动配置签名」。后台 PHP 用 libsodium 生成 Ed25519 密钥对，并通过 GitHub Secrets 的公钥加密接口提交私钥到 \`PHONEHUB_SERVER_SIGNING_KEY_B64\`；**服务器不持久化签名私钥，也不保存 GitHub Token**。GitHub Actions 使用该 Secret 自动签名和验签，并向国内镜像同步签名清单。

此时仅保存 \`storage/self-update-pending.pub\`；待 GitHub Action 发布成功及镜像同步后点击「验证镜像并启用签名」，系统验证整个 ZIP 的哈希、版本和独立 Ed25519 签名，成功才原子转为 \`storage/self-update-trust.pub\`。镜像未同步、私钥配置错误或签名不匹配时，绝不强制启用公钥。已有正式公钥不能由后台一键重建覆盖。

完整字段、默认掩码及四种设备黑名单机制，参见 [统一设备管理与签名说明](设备管理与签名-v0.5.2.md)。未配置 GitHub Token 的站点不能自动获得仓库签名权限；首次配置后 GitHub Actions 才能持续自动签名。

### 可选：管理电脑离线初始化（v0.5.1，保留兼容）

**保留固定公钥 Ed25519 数字签名，不改成字符串密钥或“下载后自己签名”。**

首次启用只需要在已授权的管理电脑上执行一次初始化脚本，后续 GitHub main 有程序更新时通过 GitHub Actions 自动签名、验签并提交签名清单。国内镜像继续提供原地址 ZIP，生产服务器安装前仍使用**事先固定在服务器上的公钥**验证文件哈希与签名。没有正确签名绝不安装。

初始化流程由 \`tools/bootstrap-self-update.php\` 串联，自动完成：

1. 在管理电脑用户目录 \`~/.phonehub/self-update/\` 生成并保存 Ed25519 密钥对（现有密钥校验后复用，**不会自动重建或轮换**）。
2. 经已经登录的 GitHub CLI，将私钥作为仓库 **GitHub Actions 加密 Secret** \`PHONEHUB_SERVER_SIGNING_KEY_B64\` 传输；私钥不会写入 Git 仓库、命令行参数或工作流日志。
3. 触发 \`sign-server-update.yml\`，GitHub Actions 在受限运行器中生成签名清单、使用公钥验签，将 \`deploy/self-update-manifest.json\` 与 \`deploy/self-update-manifest.sig\` 提交仓库。
4. 初始化脚本从 \`https://git.wksite.cn/popowk/data/archive/refs/heads/main.zip\` 读取签名包，使用本地公钥验证每个程序文件。镜像尚未同步时会重试；超时或验签失败则**拒绝安装服务器信任公钥**。
5. 仅在验证成功后，通过已经授权的 SSH/SCP 自动将原始 32 字节公钥复制到生产服务器 \`storage/self-update-trust.pub\`，核对 SHA-256 指纹；若服务器已有**不同**的固定公钥则拒绝覆盖。

**一次性命令**（在本机 clone 的仓库根目录运行，替换 SSH 主机和宝塔网站路径）：

~~~bash
php tools/bootstrap-self-update.php --server=root@你的服务器 --site=/www/wwwroot/data.tmd.pet/license
~~~

前提：管理电脑安装 PHP CLI（sodium/curl/zip）、\`gh\`（已使用 \`gh auth login\` 授权此仓库），并提前配置可自动认证的 SSH 密钥；服务器 SSH 用户拥有目标 \`storage/\` 目录写入权限。没有仓库 Actions Secret 写入权限或服务器 SSH 权限，脚本会安全失败，而不能在无凭据的条件下自行取得这些权限。

可只验证本机密钥准备流程、不更改 GitHub 或生产服务器：

~~~bash
php tools/bootstrap-self-update.php --prepare-only
~~~

**后续自动化：** \`main\` 有需要发布的程序文件变动时，GitHub Actions 自动签名和验证；提交签名清单使用 \`GITHUB_TOKEN\`，不触发递归工作流。生产后台原有「检查更新 → 安装更新」会自动验签、拒绝无签名/伪造签名/篡改内容和版本回退。只有服务器中存在固定公钥后才进入强制签名模式；旧站点升级时仍兼容 HTTPS 镜像，不能宣称旧站点已经具备独立签名验证。

**安全边界：** 自动签名让私钥保存在 GitHub Actions Secret 中，保护水平与纯离线私钥不同。必须启用主分支保护、限制工作流修改权限和 GH Actions Secret 管理权限；能够修改可信分支或签名工作流、读取该 Secret 的攻击者可能发布恶意的合法签名。建议定期将生成密钥加密离线备份，并保留明确的公钥轮换程序，不要把私钥拷贝进网站目录。客户端核心 ZIP 的 Ed25519 签名仍是另一套密钥，与本机制相互独立。

## 2. 升级前的检查

登录主管理员，进入「系统更新」：

1. 点击「运行环境自检」，核对 PHP 8.2+、pdo_mysql/curl/zip/sodium、核心文件、MySQL 迁移及目录写入权限。
2. 请在宝塔 Nginx 站点配置中确认禁止访问 `/license/storage/`，不要只依靠 Apache `.htaccess`。
3. 先备份数据库和重要密钥，且确认备份文件有离站副本。
4. 在低访问时段升级，检查新版登录页和每个核心管理页面。

环境自检中标记“需人工确认”的项目不会假装已经通过外部网络验证。

## 3. 必须一起备份的内容

| 项目 | 作用 | 注意 |
|---|---|---|
| MySQL 数据库 | 客户账号、授权、日志、加密设置、会话等 | 按一致性快照/事务导出，核对导出结果 |
| `storage/config.php` | 数据库连接配置 | 包含密码，不得放在公开目录或发送给他人 |
| `storage/ai-master.key` | 解密服务器 AI Key | 丢失后原数据库密文无法解密 |
| `storage/mobile-identity.key` | IMEI HMAC 身份密钥 | 丢失或更换会影响已有 IMEI 黑名单匹配 |
| `storage/updates/signing.key` | 软件更新签名私钥 | 丢失后旧客户端公钥可能无法验证新发布版本 |
| `storage/self-update-trust.pub` | 后台自更新固定信任公钥（启用时） | 备份并核对指纹，不能信任更新包自带公钥 |
| `storage/updates/` | 已发布的客户软件更新包 | 数据库版本记录和实际 ZIP 必须保持对应 |
| `storage/backups/` | 历史程序升级备份 | 仅备份程序代码，不等于数据库备份 |

建议在服务器之外保存**加密的**备份，测试恢复时使用隔离环境。备份中的用户数据和密钥不能发往公共仓库。

### MySQL 5.7 导出建议

通过宝塔「数据库 → 备份」进行数据库备份是最简单的操作方式；同时确认备份任务运行成功并下载一份加密离站副本。

如采用命令行，优先使用受限权限的 MySQL 配置文件传递连接凭据，而不是把密码直接写在命令行参数或 shell 历史中。对 InnoDB 表优先使用 `mysqldump --single-transaction --routines --triggers --events`，并检查退出码及文件大小。若存在非事务表，应额外规划一致性措施。

## 4. CLI 自动加密备份与离线验证（v0.5）

新增 \`tools/backup-server.php\`（**只允许运行 PHP CLI，HTTP 请求无法触发**）。使用服务器上预先配置的接收者 Curve25519 **公钥**加密数据库及关键存储文件，离线私钥绝不能上传到服务器。使用 libsodium sealed box 封装一次性对称密钥，再通过 secretstream XChaCha20-Poly1305 分块加密，避免将完整数据库复制进 PHP 内存。

备份包括：MySQL 5.7 \`mysqldump --single-transaction\` 导出的 SQL、\`storage/config.php\`、存在的 AI 和 IMEI 密钥、客户端更新签名密钥、服务器更新信任公钥，以及 \`storage/updates/\` 下的正规发布 ZIP。**不会复制旧的 \`storage/backups/\` 目录来制造递归备份。** 备份期间短暂生成受限权限的 MySQL 连接配置临时文件，完成或失败后立即清理。

### 第一次部署前（一次性）

1. 在**离线可信电脑**生成 Curve25519 密钥对。仅将**原始 32 字节公钥**上传到服务器 \`storage/backup-recipient.pub\`。**原始 32 字节私钥**留在离线电脑，不允许通过邮件、聊天软件、GitHub 或网站上传。
2. 确认服务器安装 PHP CLI 8.2+、sodium、MySQL 5.7 的 \`mysqldump\` 命令行工具，并在网站目录之外创建仅管理员可访问的备份输出目录。
3. 使用宝塔「计划任务」创建定时 Shell 任务，示例：

\`\`\`bash
/usr/bin/php /实际网站目录/license/tools/backup-server.php create /实际备份目录/phonehub
\`\`\`

路径需使用生产环境的实际路径。输出文件是 \`.phbk\`，备份目录必须位于**网站根目录之外**。没有公钥或无法连接数据库时会拒绝生成备份，不会退化为明文导出。

### 离线校验和隔离恢复

在离线可信电脑上使用项目中的同名脚本及留存的私钥：

\`\`\`bash
php tools/backup-server.php verify /backup/phonehub-example.phbk /offline/recipient-private.key
php tools/backup-server.php restore /backup/phonehub-example.phbk /offline/recipient-private.key /tmp/new-isolated-restore
\`\`\`

\`verify\` 检查所有加密分块的真实性、文件 SHA-256、结尾标记和文件数量；\`restore\` **只解压到全新隔离目录，不会自动执行 SQL 或覆盖生产数据库**。检查 \`database.sql\`、配置及密钥完整后，方可按维护流程人工恢复。需要定期在隔离环境完成真实的 MySQL 恢复演练。

### 保留策略和限制

可选环境变量 \`PHONEHUB_BACKUP_RETENTION_DAYS=30\` 会在**本次新备份成功后**清理超过 30 天的本工具命名备份文件，但始终保留最近 3 份。默认不自动删除。清理不读取任意文件名、不跟随符号链接，不能代替异地副本的保留策略。

**当前功能边界：** 加密备份工具需要由宝塔计划任务调度，不包含内置调度器；还没有自动向外部存储上传、恢复生产数据库或在线密钥托管。备份涉及 SQL 和密钥，应在隔离环境验证可恢复性，不能仅凭生成 \`.phbk\` 就认定容灾完成。

## 5. 发生 HTTP 500 或白屏

- **不要清空数据库或删除 `storage`。**
- 先查看网站对应 PHP-FPM/PHP 错误日志（不是只有 Nginx 访问日志），找到第一次 `Fatal error`、`Failed opening required` 或 `PDOException`。
- 检查 `app/accounts.php`、`app/core.php` 等运行时依赖是否存在；使用 `php -l` 检查对应 PHP 文件语法。
- 如果安装成功但 OPcache 没有刷新，在确认文件已备份后重启站点对应 PHP-FPM 进程。
- 如果更新过程中断且文件损坏，由管理员核对 `storage/backups/` 中最近一次程序备份，并先在隔离目录验证完整性，再恢复；不要直接覆盖整个 `storage`。

注意：程序文件回滚不会自动撤销数据库迁移。未来新增数据库结构必须继续遵循兼容、幂等且可恢复的迁移规则。

## 7. 历史诊断报告与开户套餐（v0.5.4，诊断页已移除）

### 一键生成排障报告

v0.5.4 曾提供独立故障诊断页面和报告复制功能；自 v0.5.16 起该页面、报告接口和按钮已移除。请改用「系统更新 → 运行环境自检」，检查 PHP、扩展、数据库、程序模块和签名状态。需要排查 HTTP 500 时，由管理员在宝塔查阅并脱敏 PHP 错误日志。

报告包含程序版本、PHP 运行版本、MySQL 主版本、数据库迁移版本、核心模块完整性、目录写入检查、独立签名是否已启用、近期更新动作的**类型和时间**，不读取原始错误日志，不包括客户账号、手机号、IMEI、IP 地址、数据库连接密码、Token、签名私钥或完整文件路径。主管理员以外无法调用报告 API。

若 PHP 入口本身已经 HTTP 500，页面可能也打不开；此时仍需在宝塔 PHP 错误日志中找到对应时间的 Fatal error，**自行遮盖敏感信息**再发送。此功能不修改已有 Ed25519 签名密钥，也不会触发签名操作。

### 仅开户时选择套餐

创建客户时必须选一个**开户额度模板**：

| 模板 | 电脑名额 | 安卓手机名额 |
|---|---:|---:|
| 单机版 | 1 | 1 |
| 标准版 | 3 | 5 |
| 团队版 | 10 | 20 |
| 自定义 | 由管理员填写 | 由管理员填写 |

后端按选中的预设覆盖提交的电脑、手机额度，防止浏览器值与实际套餐不一致。套餐不自动开放 MCP、Skill、AI Key 等高级权限；这些仍由已有授权字段和云端总开关控制。**不增加购买价格、订单、付款或自动续费功能。**

数据库仅增加 `phonehub_user_meta.opening_plan_code` 的可空字段（迁移版本 9），旧客户授权数据不会更改。v0.5.11 起，客户编辑页可以主动修改当前套餐。仅单独调整客户额度时，继续保留原套餐标签；显式切换时同步更新客户当前套餐代码及电脑、手机名额。原字段现表示当前套餐，不再作为不可修改的开户历史快照。

## 8. 套餐管理与备份接收密钥（v0.5.5）

### 套餐管理

主管理员进入「套餐管理」，可新增套餐、编辑名称及额度、调整排序和启用/停用。默认有单机版、标准版、团队版三个模板，同时保留开户时的「自定义」选项。模板只有电脑名额（1–100）和安卓手机名额（0–1000），**不包含价格、订单、支付、自动续费、软件产品或附加的 AI/MCP 权限**。

创建客户时仅显示已启用的套餐。套餐代码由服务器生成或保留原有预设代码，不能手动修改；后台按模板额度实际写入，忽略浏览器篡改的额度值。编辑/停用模板不会自动修改已有客户的电脑、手机额度。v0.5.11 起，已存在客户也可以主动切换至其他已启用套餐，此时按新套餐重设额度；已停用套餐可以保留在当前客户上，但不可新分配。已修改的套餐归属可通过管理员审计追溯。

数据迁移版本 10 只增加 `phonehub_plan_templates` 表，并以幂等方式创建三个默认模板，不删除客户或订单数据。

### 在授权后台生成备份接收密钥

进入主管理员侧栏「备份密钥」，首次可点击「生成备份密钥并下载私钥（仅此一次）」；浏览器通过 HTTPS 收到原始 32 字节 Curve25519 私钥的 `.key` 文件。服务器只保存 `storage/backup-recipient.pub` 中的 32 字节公钥，并记录管理员操作审计。**不会改动已经启用的 Ed25519 自更新签名密钥，两个系统各有独立的密钥对。**

下载后请立即把私钥保存在**离线、加密且有冗余备份**的安全存储中，核实文件长度为 32 字节。私钥不可放在公开目录、GitHub、聊天窗口或普通共享盘，也不能通过后台再次查看或重新下载。系统不会自动轮换：如果丢失私钥，需要先确认现有的已加密备份是否仍有其他解密副本，不能直接覆盖当前公钥而导致无法恢复。

密钥生成完成只表示**具备加密备份能力**，不代表已生成数据库备份；要使用已有 `tools/backup-server.php` 命令行工具和异机私钥，仍应执行实际的备份/隔离恢复验证。本轮未新增备份计划任务监控、异地同步或自动恢复功能。

## 10. 后台只读管理员与统一权限（v0.5.8）

### 服务端分段耗时采样（v0.5.9）

批量心跳的耗时采样默认关闭。确需诊断时，在 PHP-FPM 进程环境中设置 `PHONEHUB_PERF_SAMPLE_PERCENT=1`（抽样 1%，允许 1–100），然后重启对应 PHP-FPM 服务；取消该变量或设为 0 即关闭。不同宝塔/PHP-FPM 配置的环境变量注入方式可能不同，设置后需用隔离测试心跳确认日志确有采样记录。

PHP 错误日志会出现不包含账号、IP、手机指纹、Bearer 或密钥的简短记录：

```text
PhoneHub heartbeat_perf status=200 total_ms=12.31 connect_ms=1.20 auth_ms=2.10 db_ms=4.50 package_ms=1.40 response_ms=0.08 queries=16
```

`connect_ms` 是 PHP 建立 MySQL 连接和设置时区的时间；`db_ms` 为采样到的 PDO prepare/execute 累积耗时（其中可能包含认证和包查询，**不能将各阶段直接相加**）；`auth_ms` 是 Token、会话、电脑设备校验；`package_ms` 是授权包版本/全局开关查询；`response_ms` 是 JSON 编码和 PHP 输出动作，不代表客户端已接收完毕。 `total_ms` 仅从 PHP 脚本入口计时，无法测量客户端 DNS、TCP、TLS 握手、代理转发以及本机启动前的等待。

若浏览器/桌面端首请求约 2 秒，应结合 Nginx `$request_time`、`$upstream_response_time` 与客户端拆分的 DNS/TCP/TLS/TFFB 指标综合核对。**不要在 access log 中记录 Authorization 请求头**。在没有实测证据前，不应仅凭客户端耗时调整连接保持或数据库索引。

### 可选批量心跳的上线边界

`client_heartbeat.batch` 为可选扩展：每次最多核验 8 台手机、16 个本地包版本。返回服务器重新核验的设备黑名单、旧绑定优先的手机额度、授权且已启用的包版本与 AI 策略；不含操作包密文、解密密钥或上游 Key。老客户端继续无参调用，不改变旧协议。任何一台手机被停用、拉黑、授权超额或 IMEI 不一致均返回 `bound=false`；只刷新核验通过的 `last_seen`。实际下载 API 仍独立重新验权。

**资源保密性需单独评估：** 原操作包接口同时返回 `envelope` 和 `content_key`，获授权客户端拥有解密条件；客户端更新 ZIP 是明文压缩包，Ed25519 与 SHA-256 只验证来源和完整性，不能阻止授权客户端提取。必须部署 HTTPS、禁止公网直接访问 `storage`、避免 Bearer Token 泄漏；可考虑后续增加设备证明/短期下载授权与审计，但不宣称软件包不可逆向。

## 12. 重要安全项：阻止公网直接访问 storage（v0.5.10）

`storage/` 可能包含数据库配置、设备身份密钥、AI 加密主密钥、客户端签名私钥与更新 ZIP。**服务器必须禁止通过网页 URL 直接访问整个目录；只允许 PHP 进程在本地文件系统中读取。**

本版本已在项目根目录 `.htaccess` 添加 Apache 的 `storage/` 路径拒绝规则及密钥/压缩包扩展名兜底。**但宝塔 Nginx 不读取 .htaccess，这项提交不会替你修改线上 Nginx。** 在实际服务 `server { ... }` 内增加并加载以下规则（网站部署在 `/license/` 路径时）：

```nginx
location = /license/storage { return 403; }
location ^~ /license/storage/ { return 403; }
```

保存前请检查与现有 location、PHP 处理和反向代理规则是否冲突；执行 `nginx -t` 成功后再安全重载。若部署在不同 URL 前缀，必须替换对应路径，且在 CDN/ESA、IPv4 与 IPv6 的所有直连入口统一生效。**不要将整个 /license/ 禁止掉**，否则客户端 API 和后台都会中断。

可以在真实 `storage/` 下临时放置仅包含无敏感内容的随机名称测试文本文件，以公网匿名 GET 请求访问该文件，预期必须为 403；测试结束立即删除。**不要使用 config.php、私钥或真实 ZIP 进行公网测试，不要下载敏感文件验证。** 同时分别检查 HTTP、HTTPS、IPv4/IPv6 直连与 CDN 入口；目录列表关闭不等于文件不可直连。

本项只有生产 Nginx 实测拒绝后才能标为验收通过；本地 CI 对 `.htaccess` 的静态检查不能证明 Nginx 配置有效。

## 14. v0.5.13 旧版固定公钥更新兼容过渡

### 产生问题的原因

旧版服务端正在运行的 app/updater.php 仍按旧 UPDATE_FILES 检查 ZIP。历史列表包含 docs/客户端接入API-v0.3.md 与 docs/客户端接入API-v0.4.md。最新版 GitHub 删掉了这两个文件，即使最新版 updater.php 已删旧路径，运行中的旧 updater 仍会拒绝升级。更重要的是，旧 updater 对已固定 Ed25519 公钥的服务器要求签名 manifest 的文件键及所有哈希与其旧列表**完全一致**。单纯补空文件或移除新代码引用，不能解决签名不兼容。

- deploy/self-update-manifest.json + .sig：**严格匹配 v0.5.10/v0.5.11 安装的历史 29 个文件**，用既有独立 Ed25519 签名密钥生成，专供旧 updater 读取。
- deploy/self-update-manifest-v2.json + .sig：**严格匹配当前完整运行文件清单**，包括 app/automation.php、automation/v1/index.php 等，供新 updater 读取。
- 旧 v0.3/v0.4 文档在仓库中仅保留无运行代码、明确标注已弃用的最小兼容文件，现代 UPDATE_FILES 不再安装这两个文件。
- 两组清单都必须通过同一既有公钥验签，不能删除/替换已固定的信任公钥，不允许未签名包。

### 老服务器升级流程：两次检查与安装

1. 检查 GitHub 签名工作流成功，且国内镜像 main.zip 已包含四份签名清单及两个废弃文档路径；先备份数据库、storage、客户端核心更新签名私钥以及自更新固定公钥。
2. 在旧服务器管理后台打开「系统更新」并执行更新。旧版 updater **第一次只会安装历史 29 个文件**，可将 app/updater.php、index.php、version.json 升为 v0.5.13，但不能安装自己当时清单未包含的新 app/automation.php、automation/v1/index.php 等。
3. 留在「系统更新」页面，再次点击「检查更新」。新版 updater 会识别缺失模块，并允许**同版本修复补齐**。执行后通过 v2 清单严格验签，安装完整运行文件。
4. 再次检查必须确认 signature_verified=true、signature_required=true、missing_modules=[]；随后验证核心更新发布页和自动化 API。第一次更新到 v0.5.13 后并不代表新模块已经全部安装。

## 15. v0.5.14 automation/v1 子目录安装失败修复

### 错误原因

旧安装器在安装前检查文件目标父目录是否存在，最多只允许缺失一级。新增的 automation/v1/index.php 位于两级路径；全新服务器没有 automation 目录时，会报“更新目标父目录不存在：automation/v1/index.php”，即使 ZIP、Ed25519 签名和版本号本身都有效，安装仍被拒绝。程序报告“已恢复升级前程序文件”意味着此次安装已尝试回滚，不代表新代码已在服务器生效。

### 新安装器行为

自 v0.5.14 起，预检查每一级相对路径是否合法、现有路径均为普通目录且不是符号链接、最近存在的父目录允许写入；完成所有文件的验证与备份后才逐级创建缺失的目标目录，并记录此次新建的目录。复制与重命名成功后校验文件 SHA-256。如安装失败，先恢复旧文件并删除此次新建的文件，再反向尝试移除新建的空目录。对目录中原有文件绝不执行递归删除或强制移除。version.json 仍最后安装。

### 已在旧安装器报错的生产服务器如何恢复

1. 先对现有文件和 storage/ 签名与数据库做备份。确认下载源已包含 v0.5.14 且四份服务器自更新签名清单已由 GitHub Actions 签名生成。若仍用旧更新器失败，它的 PHP 代码在这次请求中尚未被替换，GitHub 新版本**不能自动修复已运行的旧安装器**。
2. 在宝塔文件管理器中进入 PhoneHub 的**网站程序目录**（即含 index.php、app、api、storage 等文件夹的目录），手工创建 automation 文件夹，再在其中创建 v1 文件夹。最终应存在 automation/v1/ 目录，**无需手工放入或复制 index.php**。确认 PHP-FPM 的运行用户对这两个目录具有文件创建权限，且这两个目录不是符号链接；禁止 chmod 777，也不要把 storage 放到可公开下载位置。
3. 如果使用服务器终端，可在正确的 PhoneHub 程序根目录执行 `mkdir -p automation/v1`，并通过 `ls -ld automation automation/v1` 检查。若使用 root 创建，需根据宝塔站点实际 PHP-FPM 用户调整目录属主/写入权限，不能假设 PHP 用户一定是 www。
4. 重试“系统更新”。旧更新器看到真实可写的父目录后，才可能完成本次更新。随后再次检查更新并执行“补齐缺失模块”（如果提示），最终验证 `missing_modules=[]`、服务端签名已通过、管理界面和自动化 API 正常。更新过程中不要删除固定公钥或关闭签名验证。
5. 如果仍失败，核实是权限不足、符号链接路径、CDN 国内镜像未同步，还是签名清单版本不一致；不要直接运行来源不可信的 PHP 文件或绕过验签。

### 回归测试

tests/updater-install-smoke.php 增加 automation/v1 二级目录在安装前完全不存在的真实安装测试，模拟在最后版本替换前抛异常，确认旧文件恢复且刚创建的 automation/v1 和 automation 空目录被清理；再验证正常升级能够生成目录，并拒绝用符号链接或普通文件充当目录。既有 Ed25519 双清单签名、MySQL 5.7 和客户端接口回归保持原状。

- mobile_bind、mobile_check、mobile_heartbeat、mobile_list 加入向后兼容的状态字段 imei_bound、imei_stored、phone_number_bound、phone_model_received；绝不返回原号或密钥。
- 真正的 APP 仍须主动在 mobile_bind 或 mobile_heartbeat 里送入合法可获得的身份字段。此 GitHub 仓库不包含客户端源码，单改服务端无法让旧客户端自动上报；Android 10+ 普通应用无法可靠获取 IMEI，部分 SIM 没有本机号码。
- 客户端的 client_heartbeat.batch 中 imei 按现有协议仅作身份核验，不会偷偷将原始值持久化。缺少授权时保留空字段，不能造假。
- 确保使用 HTTPS、Bearer 登录令牌和对应电脑 device_id；旧的 HMAC 密钥及加密数据不清空或轮换。
